# Implementation decisions

The user's explicit instruction to follow `EVALUATION.md` takes precedence over the one-shot prompt's instruction not to read it. The lecturer's live login/register pages were inspected; authenticated lecturer workflows were not accessible. This is a specification-based implementation, not a claim of identical authenticated screens.

| Question                                 | Decision                                                                                                                                                                                                                                                                                                      |
| ---------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Immediate delete or confirmation?        | Confirmation, as required by the evaluation rubric.                                                                                                                                                                                                                                                           |
| Pending or Active section?               | Active, matching the rubric. Overdue and Completed remain separate.                                                                                                                                                                                                                                           |
| Search tag names?                        | Explicit advanced toggle, alongside title and subtask search; filters combine with AND.                                                                                                                                                                                                                       |
| What does a template preserve?           | Subtask titles/positions, priority, recurrence, reminder, and a relative due offset. No original absolute due date, tags, IDs, or completion state.                                                                                                                                                           |
| Recurrence repeated completion requests? | One successor per original task, tracked by `recurrence_spawned` in the same SQLite transaction. Unchecking/rechecking the original cannot duplicate its successor. Successors start with their own unset marker.                                                                                             |
| Overdue recurrence?                      | Advance one interval from the original due date. This may still be overdue after a long absence; no silent skipping of occurrences.                                                                                                                                                                           |
| Dates and minimum lead time?             | UTC instants stored; inputs without offsets interpreted as SGT; at least one minute ahead on create or due-date change. Other edits to an overdue task and importing historical records remain possible.                                                                                                      |
| API implementation files?                | Consolidated feature dispatcher and separate auth dispatcher retain every specified URL/method, avoid boilerplate, and centralize the session boundary.                                                                                                                                                       |
| `middleware.ts`?                         | Next.js 16 uses `proxy.ts`, its supported replacement; the protected page routes are unchanged.                                                                                                                                                                                                               |
| Template/JSON relationships?             | Subtasks and tags included in portable JSON, all task/subtask IDs regenerated, existing tags reused case-insensitively. Re-import intentionally duplicates tasks. CSV is export-only.                                                                                                                         |
| Limits?                                  | Task/subtask titles 500 chars; tags 50; template names 100; imports 1 MB / 1000 tasks / 100 tags and subtasks per imported task. Interactive subtask creation has no fixed count limit.                                                                                                                       |
| Calendar?                                | Always 42 cells, including adjacent months; holiday seed currently covers 2026 only, with substitute Mondays. Year navigation is not a promise of other years' holiday coverage.                                                                                                                              |
| Notifications?                           | Server atomically claims eligible reminders once across tabs, then client invokes browser Notification. This provides at-most-once delivery attempts, not guaranteed delivery if a tab closes or OS blocks it. No service worker or push delivery when closed. Changing due date/reminder resets eligibility. |
| Sessions?                                | HS256, fixed issuer/audience, HTTP-only cookie, SameSite=Lax, Secure in production, seven days. A strong configured secret and stable RP domain are mandatory in production. Logout deletes the cookie; stolen JWTs are not centrally revocable before expiry.                                                |
| WebAuthn verification?                   | Required user verification, RP/origin validation, five-minute challenge stored server-side, bound by HTTP-only attempt cookie and consumed once, signature/counter verification. Both-zero authenticators remain supported by SimpleWebAuthn.                                                                 |
| Deployment?                              | One Node container + persistent SQLite volume. Native Railway GitHub deploy rather than a workflow requiring a Railway token. No production credentials committed.                                                                                                                                            |
| Theme styles?                            | Single shared stylesheet with light/dark variables; only user-selected tag swatch colors are dynamic inline styles. Colored dots never determine text contrast.                                                                                                                                               |
| Coverage?                                | Unit coverage measures database/domain/date logic. Browser tests cover auth, UI and route integration. Do not interpret core unit coverage as whole-application coverage.                                                                                                                                     |

## Known operational limits

Single-host SQLite is appropriate to this workshop. Scaling replicas requires a shared database design. Passkey recovery, account deletion, multi-device passkey enrollment management, distributed rate limiting, centrally revocable sessions, and background push notifications are future work, not implied by this submission. The process-local passkey options limiter is scoped to username and is not a comprehensive production abuse-control service.
